# ADR-002：单文件形态下的测试与 lint 方案

- 状态：accepted（门禁② 批准 @2026-07-31）
- 日期：2026-07-31
- 关联：SPEC-1~5/7/9~12 · plan 技术选型 · 预审 #8（原 plan 引用了本仓不存在的 ADR-010/US-13）

## 背景与驱动力

ADR-001 定了单文件内联形态，随之而来的问题：**逻辑怎么测、产品文件怎么 lint**。预审实测：把整个 `<script>` 块交给 node 求值必炸（`ReferenceError: document is not defined`），所以"用 node 测逻辑"这句话本身需要一个可执行的路径。

## 备选方案

### 选项 A：分层标记 + 抽块求值
用固定注释标记切出 LOGIC/STORE/UI 三块；测试时按标记抽出前两块，`new Function(...)` 求值后断言。存储层函数接受注入的 store（测试传内存 Map）。
- 优点：**实测可跑**（预审已验证 `validateAmount("12.5")=false`、`netTotal([300,-500,200])=0`）；零依赖；标记同时成为分层 fitness function 的锚点
- 代价：实现者必须遵守标记纪律（靠 SPEC-12 的 fail-closed 断言兜底）；UI 层仍无自动化测试

### 选项 B：引入 headless 浏览器（Playwright/Puppeteer）做 UI 验收
- 优点：能测真实 UI 流程与 localStorage，覆盖 SPEC-4~9 的**用户契约**（而非仅纯函数）
- 代价（异构评审 #9 修正——原写"违背 SR-3 零依赖"是**错误解释**：SR-3 约束的是**产品运行时**，交付物仍是单 HTML，**开发期依赖不违反它**）：真实代价是 CI 需装数百 MB 浏览器、时间从秒级到分钟级、维护 selector 的长期成本；**且 Playwright WebKit ≠ 真 Safari**，仍替代不了实机验证

### 选项 D：混合（Node 单测 + CI 浏览器冒烟 + 实机 Safari 人工）
- 优点：分层覆盖最完整——纯函数用 A 秒级反馈，用户契约用浏览器冒烟兜底，Safari 特性人工兜底
- 代价：三套机制的维护面；对 3 步骨架 demo 而言，浏览器冒烟这一层的收益/成本比最低

### 选项 C：不做自动化测试，全靠人工 checklist
- 优点：零成本
- 代价：违反宪法 C2（能用可执行验证的绝不用"我觉得对了"）；金额校验与累加这类纯逻辑**完全可以自动测**，放弃没有正当理由

## 决定

选 A（**本 demo 范围内**），并显式记录：**D 是更完整的方案，之所以不选是 Appetite 而非技术判断**——3 步骨架 + 一个月试点内，浏览器冒烟层的搭建与维护成本超出预算。企业项目落地时应默认选 D（手册须写明这点，避免培训对象把 A 误读为通用最佳实践）。

lint 侧配套决定：**产品文件由 `check-single-file.sh` 覆盖**（外链/行数/分层三类断言），**不挂 ratchet**——平台内置 selfcheck 只扫 `*.sh`，对 `index.html` 零覆盖，挂上去是结构性假绿（预审 #5）。

## 后果

- ✅ 逻辑契约真正可执行验证；分层标记一物两用（可测性 + fitness function 锚点）
- ⚠️ UI 层与浏览器兼容性（NFR-1）**无自动化**：降为人工 checklist，结果在门禁④留痕——如实标注，不伪装成断言（预审 A2）
- ⚠️ **用户契约未被自动验证**（异构评审 #5）：SPEC-4~9 的纯函数部分有断言，但"提交→写入→刷新→仍在→汇总正确"这条端到端链路只有人工 checklist。**这是本 demo 明确接受的覆盖缺口**，不是疏漏
- ⚠️ SPEC-12 的分层断言是**词法守卫非架构证明**（异构评审 #2）：别名、动态属性访问、`globalThis[...]` 拼接均可绕过——挡手滑不挡蓄意
- 可复议条件：功能超出 3 步骨架、或出现真实用户报的 UI 缺陷 → 重估选项 B（新 ADR）
