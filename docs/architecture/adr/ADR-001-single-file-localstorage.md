# ADR-001：单文件 HTML + localStorage，不引入任何构建与后端

- 状态：accepted（门禁② 批准 @2026-07-31）
- 日期：2026-07-31
- 关联：SR-3 · NFR-2/4 · prfaq 差异化主张

## 背景与驱动力

这是个人离线小工具，Appetite 硬限 3 步功能。选型必须服务于"双击即用、数据不出本机、零维护"。

## 备选方案

### 选项 A：单文件 HTML + localStorage
- 优点：双击即用、零安装零构建、零后端成本、数据天然不出本机（隐私）；作为 demo 也最容易讲清
- 代价：清缓存/换浏览器即丢数据；无法多设备；单文件行数上限约束功能扩展

### 选项 B：单文件 HTML + IndexedDB（同样无构建）
- 优点：无 5MB 容量上限；支持索引与结构化查询；数据量增长后仍从容
- 代价（异构评审 #8 二次修正——原写"异步会迫使逻辑层变 Promise 链"仍不诚实：**异步只影响 STORE 与控制器，纯逻辑层不受影响**）：真实代价是 IndexedDB 的**样板与错误面**（open/onupgradeneeded/事务/版本迁移）在 400 行预算里占比过高；而本场景数据量 <100KB，其容量与索引优势为**零收益**；且 ADR-003 实测表明 IndexedDB 在 file:// 下**同样是共享 origin**，连隔离性都换不到
- 注：**IndexedDB 不需要任何构建**（预审 #9 指出原稿以「引入构建链」否决它属稻草人，已改正）

### 选项 C：带后端的小服务（如 SQLite + 简单 API）
- 优点：数据可靠、可多设备、有真正的 origin 隔离
- 代价（异构评审 #8 修正——原写"必然要账号"不成立，**后端不必然要账号**）：真实代价是引入**部署、网络可用性、安全面（暴露端点）与长期运维**；对一个个人离线小工具，这些成本没有任何回报

## 决定

选 A。决定性理由：本场景数据量 <100KB，B 的容量/索引优势为零收益、样板却吃掉 400 行预算的可观比例，且 ADR-003 证明它连 origin 隔离都换不到；C 的部署/网络/安全/运维成本对个人离线工具无回报。**A 的代价（数据可能丢失、同 origin 可读）已在 prfaq FAQ 与 ADR-003 显式接受并写进用户可见说明**。

## 后果

- ✅ 双击可用、隐私天然、维护成本近零；demo 讲解简单
- ⚠️ 数据可能丢失——**已在 prfaq FAQ 明确接受**；导出功能列入 backlog 而非本次范围
- 可复议条件：若观察窗证明记录习惯成立且用户要求多设备 → 重开选型（新 ADR）
